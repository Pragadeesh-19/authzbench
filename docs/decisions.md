# Decisions

Every choice that shapes a published number, with the evidence behind it. A row is never edited to change its
meaning; a later row supersedes it and says so.

| ID | Topic | Decision | Source |
|----|-------|----------|--------|
| A1 | Clock | The Go driver reads the performance counter on Windows and Go's monotonic clock elsewhere. Go's monotonic clock on Windows advances in steps of about 0.5 ms (measured: 541 µs to 1.06 ms), which would report a fast check as 0 ns. `timing_test.go` requires every platform to resolve less than 1 µs. The Python driver uses `time.perf_counter_ns`, which already does. | build time, 2026-11-06 |
| A2 | Revocation race | A race starts only once the probe is allowed at the mode being measured, waiting at most the cap. The previous race writes the revoked relationship back, and a stale mode can take up to its staleness to see that write; starting at once found the probe denied. Both drivers, with a test that runs two races back to back. | build time, 2026-11-06 |
| A3 | SpiceDB modes | Fresh is `fully_consistent` ("explicitly bypasses caching"); fastest is `minimize_latency`, the default for `CheckPermission`, stale by up to the 5 s quantization window (`--datastore-revision-quantization-interval`, default 5s, plus `--datastore-revision-quantization-max-staleness-percent`, default 0.1). `--dispatch-max-depth` is 50. Sources: https://authzed.com/docs/reference/api-consistency and `spicedb serve --help` of v1.57.0. | build time, 2026-11-06 |
| A4 | OpenFGA modes | Fresh is `HIGHER_CONSISTENCY`; fastest is `MINIMIZE_LATENCY`. OpenFGA runs with `OPENFGA_CHECK_QUERY_CACHE_ENABLED=true` (TTL 10 s by default): with caching off, the documented default, both modes read the database and "fastest" would not be OpenFGA's fastest. The cache is its documented latency tuning, so the setting favours OpenFGA. Breaking the fresh mode to `MINIMIZE_LATENCY` fails the revoke test, so the cache is live. `--resolve-node-limit` is 25, above the 16-group nesting scenario. Sources: https://openfga.dev/docs/interacting/consistency, https://openfga.dev/docs/getting-started/setup-openfga/configuration and `openfga run --help` of v1.22.1. | build time, 2026-11-06 |
| A5 | Datastores | SpiceDB and OpenFGA each run on their own PostgreSQL 17, the production datastore both document; never the in-memory datastore. Every image is pinned by digest in `services/compose.yaml`. | build time, 2026-11-06 |
| A6 | Versions | SpiceDB reports its own version (the `io.spicedb.debug.version` trailer) and the results record it. OpenFGA exposes no version over its API, so the operator states it and it must match the pinned image. | build time, 2026-11-06 |
| A7 | Loading | A load leaves the engine holding exactly the dataset: SpiceDB deletes every relationship of the dataset's resource types first; OpenFGA gets a new store per load. Writes go in the largest batch each server accepts by default (SpiceDB 1,000 updates, OpenFGA 100 tuples). Load time is not measured. | build time, 2026-11-06 |
| A8 | Go version | The Go module needs Go 1.25.8, the floor of the official SpiceDB client (authzed-go v1.11.0). Clients are added at their minimum versions; taking the newest gRPC or genproto would raise the floor to 1.26 for nothing the driver uses. CI tests the floor and the newest Go. | build time, 2026-11-06 |
| A9 | Checks in flight | The Go driver's open loop keeps up to `-in-flight` checks outstanding (default 256); each is still timed from when it was due, and a check that waits for a free slot is charged that wait. With one check at a time, a service at 13 ms per check saturates at about 75 checks/s and the driver, not the service, becomes the queue (measured: SpiceDB p50 33 s at 1,000/s on a laptop). wrk2 and YCSB, which the plan names (eng D2), keep many requests outstanding. The Python driver calls Nodus on the calling thread, one check in flight, as an application calls an embedded engine; that disadvantage lands on Nodus (S1). Every open-loop row publishes its `in_flight`. | build time, 2026-11-06 |
| A10 | OpenFGA connections | The OpenFGA SDK falls back to Go's default HTTP client, which keeps 2 idle connections per host; with many checks in flight it would open and close a TCP connection for most checks, a cost of the driver charged to OpenFGA. The adapter gives the SDK a client that keeps one idle connection per check in flight. SpiceDB's gRPC client multiplexes every check over one HTTP/2 connection and needs nothing. | build time, 2026-11-06 |
| A11 | Denied by | Every revocation result also records `denied_by_ns`: the time from the revoke's acknowledgement until the first denying check returned (null when capped). Staleness runs to that check's start, so a check that waits inside the call for the revoke, as a Nodus follower does when given the revoke's token, would publish a staleness near zero while the wait hid inside the check; a service's fresh mode hides one network round trip the same way. The two numbers together show when the probe stopped being allowed and when the application had its denial. Both drivers and the shared schema; a test with a checker that waits 300 ms inside the call pins staleness 0 and denied-by 300 ms plus the check. Decided by the owner, 2026-11-07 | build time, 2026-11-07 |
