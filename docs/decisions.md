# Decisions

Every choice that shapes a published number, with the evidence behind it. A row is never edited to change its
meaning; a later row supersedes it and says so.

| ID | Topic | Decision | Source |
|----|-------|----------|--------|
| A1 | Clock | The Go driver reads the performance counter on Windows and Go's monotonic clock elsewhere. Go's monotonic clock on Windows advances in steps of about 0.5 ms (measured: 541 µs to 1.06 ms), which would report a fast check as 0 ns. `timing_test.go` requires every platform to resolve less than 1 µs. The Python driver uses `time.perf_counter_ns`, which already does. | build time, 2026-11-06 |
| A2 | Revocation race | A race starts only once the probe is allowed at the mode being measured, waiting at most the cap. The previous race writes the revoked relationship back, and a stale mode can take up to its staleness to see that write; starting at once found the probe denied. Both drivers, with a test that runs two races back to back. | build time, 2026-11-06 |
| A3 | SpiceDB modes | Fresh is `fully_consistent` ("explicitly bypasses caching"); fastest is `minimize_latency`, the default for `CheckPermission`, stale by up to the 5 s quantization window (`--datastore-revision-quantization-interval`, default 5s, plus `--datastore-revision-quantization-max-staleness-percent`, default 0.1). `--dispatch-max-depth` is 50. Sources: https://authzed.com/docs/reference/api-consistency and `spicedb serve --help` of v1.57.0. | build time, 2026-11-06 |
| A4 | OpenFGA modes | Fresh is `HIGHER_CONSISTENCY`; fastest is `MINIMIZE_LATENCY`. OpenFGA runs with `OPENFGA_CHECK_QUERY_CACHE_ENABLED=true` (TTL 10 s by default): with caching off, the documented default, both modes read the database and "fastest" would not be OpenFGA's fastest. The cache is its documented latency tuning, so the setting favours OpenFGA. Breaking the fresh mode to `MINIMIZE_LATENCY` fails the revoke test, so the cache is live. `--resolve-node-limit` is 25, above the 16-group nesting scenario. Sources: https://openfga.dev/docs/interacting/consistency, https://openfga.dev/docs/getting-started/setup-openfga/configuration and `openfga run --help` of v1.22.1. | build time, 2026-11-06 |
| A5 | Datastores | SpiceDB and OpenFGA each run on their own PostgreSQL 17, the production datastore both document; never the in-memory datastore. Every image is pinned by digest in `services/compose.yaml`. | build time, 2026-11-06 |
| A6 | Versions | SpiceDB reports its own version (the `io.spicedb.debug.version` trailer) and the results record it. OpenFGA exposes no version over its API, so the operator states it and it must match the pinned image. | build time, 2026-11-06 |
| A7 | Loading | A load leaves the engine holding exactly the dataset: SpiceDB deletes every relationship of the dataset's resource types first; OpenFGA gets a new store per load. Writes go in the largest batch each server accepts by default (SpiceDB 1,000 updates, OpenFGA 100 tuples). Load time is not measured. | build time, 2026-11-06 |
| A8 | Go version | The Go module needs Go 1.25.8, the floor of the official SpiceDB client (authzed-go v1.11.0). Clients are added at their minimum versions; taking the newest gRPC or genproto would raise the floor to 1.26 for nothing the driver uses. CI tests the floor and the newest Go. | build time, 2026-11-06 |
| A9 | Checks in flight | The Go driver's open loop keeps up to `-in-flight` checks outstanding (default 256); each is still timed from when it was due, and a check that waits for a free slot is charged that wait. With one check at a time, a service at 13 ms per check saturates at about 75 checks/s and the driver, not the service, becomes the queue (measured: SpiceDB p50 33 s at 1,000/s on a laptop). wrk2 and YCSB, which the plan names (eng D2), keep many requests outstanding. The Python driver calls Nodus on the calling thread, one check in flight, as an application calls an embedded engine; that disadvantage lands on Nodus (S1). Every open-loop row publishes its `in_flight`. | build time, 2026-11-06 |
| A10 | OpenFGA connections | The OpenFGA SDK falls back to Go's default HTTP client, which keeps 2 idle connections per host; with many checks in flight it would open and close a TCP connection for most checks, a cost of the driver charged to OpenFGA. The adapter gives the SDK a client that keeps one idle connection per check in flight. SpiceDB's gRPC client multiplexes every check over one HTTP/2 connection and needs nothing. | build time, 2026-11-06 |
| A11 | Denied by | Every revocation result also records `denied_by_ns`: the time from the revoke's acknowledgement until the first denying check returned (null when capped). Staleness runs to that check's start, so a check that waits inside the call for the revoke, as a Nodus follower does when given the revoke's token, would publish a staleness near zero while the wait hid inside the check; a service's fresh mode hides one network round trip the same way. The two numbers together show when the probe stopped being allowed and when the application had its denial. Both drivers and the shared schema; a test with a checker that waits 300 ms inside the call pins staleness 0 and denied-by 300 ms plus the check. Decided by the owner, 2026-11-07 | build time, 2026-11-07 |
| A12 | Second machine | Machine 1 runs every writer: `authzbench serve` holds the Nodus writer (a durable graph that ships its log to S3) or the calibration engine behind JSON over persistent HTTP/1.1, binds the address it is given and drops any connection from an address not in `--allow`; SpiceDB and OpenFGA bind `BIND_ADDRESS` (127.0.0.1 unless set). Machine 2 runs the driver: `nodus-follower` sends writes to machine 1 and checks a Nodus follower in the driver's process, fresh with the latest write's token and fastest without one; `remote-calibration` sends both to machine 1 and proves the timing across the network. The driver refuses a server holding another dataset (model, scale, seed, counts), a writer on another nodusdb version, and a `--placement` that misdescribes the engine. A follower check waits for its token at most the revocation cap, so a slow follower is measured, not failed. Implements eng D3 of the launch plan | build time, 2026-11-07 |
| A13 | No Nagle delay on the wire | The engine server and the driver's remote client both set `TCP_NODELAY`. On the first cloud run (two c5.2xlarge in one eu-north-1 zone) every remote call cost about 41 ms: the server wrote a reply as headers then body, Nagle's algorithm held the body until the client acknowledged the headers, and Linux delays that acknowledgement about 40 ms. That inflated every remote write and, because staleness runs from the acknowledgement, shortened the measured staleness by the same amount. A test now requires a write and a check over loopback to take under 20 ms at the median; it failed on Linux before the fix and passes after. Windows loopback never showed the stall | cloud run, 2026-11-07 |
| A14 | Repeated revocation races | Each mode runs the revocation race 30 times (`--revocation-trials`, `-revocation-trials`), one after another, so a result is a distribution and not one draw. The results file keeps every trial under `samples` and, for staleness, denied-by, resolution and write time, the count, p50, p99 and maximum by nearest rank; staleness and denied-by count only trials seen within the cap, and `capped` says how many were not. A capped trial ends the mode's trials: it can say no more than "longer than the cap", and the next trial's wait for its restore can take as long. The file records `trials_requested` beside `trials`. The format is now `authzbench.results/2`. Both drivers; mutation-checked (seven Go and five Python mutants killed). Asked by the owner, 2026-11-07. | owner, 2026-11-07 |
| A15 | Services at their vendors' production settings | Each service gets its own Postgres 17 with the stock `max_connections` of 100 and its pools sized from it as its vendor documents, instead of the built-in defaults (SpiceDB read 20 and write 10; OpenFGA 30 open, 10 idle). SpiceDB (authzed.com/docs/spicedb/best-practices, "Tune Connections to Datastores": divide the database's connections by the instances, split them between reads and writes, set each minimum to half its maximum): read 60 and write 40, minimums 30 and 20, the 3:2 split of the guide's own example. OpenFGA (openfga.dev/docs/best-practices/running-in-production): maximum open equal to `max_connections`, 100; minimum open 30, the top of the guide's 10–30 %; minimum idle 20, about two thirds of that; maximum idle equal to maximum open, as the guide advises when connections would otherwise close and reopen; idle time 30 minutes, as it advises a long one; logs as JSON at info. Neither vendor documents a Postgres server setting a check depends on, so Postgres stays stock. Left out on purpose: TLS, authentication beyond SpiceDB's preshared key, tracing and datastore metrics, which the guides list for operating a service and which add cost to a check rather than remove it. Checked on machine 1 after recreating the services: Postgres showed 52 SpiceDB and 32 OpenFGA connections open at idle. | owner request, 2026-11-07 |
| A16 | SpiceDB's fresh read as its vendor recommends | `-spicedb-fresh` chooses how a fresh SpiceDB check reads: `fully_consistent` (the default, as before) or `at_least_as_fresh` a ZedToken, which SpiceDB's best-practices guide recommends over `fully_consistent` because the latter skips its caches ("Use ZedTokens and 'At Least As Fresh' for Best Caching", authzed.com/docs/spicedb/best-practices). The token is the race's revoke token, otherwise the token of the latest write the engine made, which is how the Nodus follower's fresh mode reads; an application that keeps its last write's token reads the same way. Each choice is its own run with the usual two modes, so the results format does not change and `minimize_latency` is measured once per run. Tested against a live SpiceDB: the reference and the race with each choice, and fresh checks that see a grant and its removal without being handed either token; six mutants killed. Asked by the owner, 2026-11-07. | owner, 2026-11-07 |
| A17 | A rate ladder | The open loop runs at 100, 500, 1,000 and 10,000 checks per second by default in both drivers, instead of 1,000 and 10,000: the first shows each engine unloaded, the second approaching what one 8-vCPU machine holds, the last two beyond it. On the S run machine 1 was 12–15 % busy at 100/s and 93–99 % at 1,000/s for SpiceDB and OpenFGA with Postgres beside them, about 10 ms of CPU per fully consistent check; the CPU traces are published with the results. Postgres stays on machine 1. Asked by the owner, 2026-11-07. | owner, 2026-11-07 |
| A18 | Open review instead of a private window | The first results are published with no private pre-launch review by the vendors. AuthzBench goes public with them, says plainly that the author of NodusDB wrote it, and invites SpiceDB's and OpenFGA's maintainers, and anyone else, to change the tuning, the adapters or the method by pull request. An accepted change gets a decision row and a new run under `runs/`; a published number is never edited in place. The owner chose openness over a waiting period, 2026-11-08. | owner, 2026-11-08 |
| A19 | Delegation race | A person delegates to one agent, which delegates down a tree three wide and four agents deep: 40 agents, 27 leaves, all on today's model (an agent is a `user`, its delegated authority a `group` nested in its delegator's). The race removes the person's one delegation, `group:delegation-person#member@group:delegation-agent#member`, and times every leaf until its first denying check; a trial's staleness and denied-by are the last leaf's, and every leaf's are kept in the sample. The person must keep their own access, and the reference evaluator must agree on both sides of the revoke before a dataset is written. A capped trial records how many leaves were still allowed. The tree draws nothing from the seed, so a seed's earlier relationships and checks are unchanged (checked on S, seed 1: the 5,487 relationships of the published run are an exact prefix of the 5,570, and the 2,000 checks are identical). Conformance adds the 27 leaves and the person, all allowed. The Python driver checks the leaves in turn, so Nodus is charged the sweep (27 checks of about 15 µs); the Go driver gives each leaf its own goroutine, as each agent checks for itself, so a service is not charged for the leaves before it. In a stale mode that keeps up to 27 checks in flight until the revoke shows, and on the machines of the 2026-11-07 run both services saturated near 1,000 checks a second, so a stale mode's resolution and denied-by can include queueing; its staleness is set by the engine's cache window. Formats become `authzbench.dataset/2` and `authzbench.results/3`. Both drivers; 21 mutants killed (14 Python, 7 Go). Act 3 of the computed-authority plan, asked by the owner. | build time, 2026-11-12 |
| A20 | Token baseline | `--engine tokens` is the copy-authority baseline the delegation race is measured against: an authorization server in the driver's process issues HS256 access tokens (JWS, `typ` `at+jwt`) and every check verifies the agent's token locally, signature, expiry, audience and scope, as a resource server verifies a JWT. An agent gets its token by exchanging its delegator's (RFC 8693); the server issues one only while the graph grants the agent. Three choices favour tokens: a token never outlives its delegator's, so a whole tree dies when its root's token does (without that rule each leaf lives out its own lifetime); HMAC costs less than the asymmetric signature most issuers use; and the default lifetime is 60 s (`--token-lifetime-seconds`), where common defaults run to an hour. Every token lives one lifetime from its issue time, and its issue time is a seeded draw within the lifetime before it was asked for, as if each agent had started at a random moment; issuing at once would put every race at the start of a lifetime. Expiry is on the driver's clock. The revocation cap must exceed the lifetime. Not modelled: introspection (RFC 7662), which is a central check and is measured already as the services' fresh modes, and pushed revocation (CAEP, Shared Signals), which we would take as a contributed baseline. Its check latency includes in-process server answers for checks without a valid token, so only its races are meant for comparison. Nine tests, six mutants killed. | build time, 2026-11-12 |
